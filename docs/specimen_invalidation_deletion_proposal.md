# 標本の無効化・完全削除の設計判断

2026-10-11に設計責任者が推奨案を承認した。採用した要件は`PROJECT_SPEC.md`の6.5節に反映する。この文書は選択理由と実装時の確認事項を残す。

## 判断が必要な理由

Phase 9は管理者による標本の無効化と完全削除を求める。現状の`Specimen`には無効化状態がなく、`QRLabel`、`SpecimenEvent`、`SpecimenPhoto`はすべて標本を`PROTECT`で参照している。履歴は通常の更新・削除を禁止し、QRの割当済みラベルは標本との1対1関係を持つ。写真の実体はDB外の保護ボリュームにある。削除を単純な`Specimen.delete()`で実装できず、公開URL・履歴・写真・監査記録の意味を先に決める必要がある。

## 推奨案

1. **無効化**は標本の物理的な状態（所蔵中・貸出中など）と分けた管理状態にする。無効化日時と実行者を保存し、標本・履歴・写真は保持する。既存の割当QRは同じDBトランザクションで`retired`にする。通常の検索・詳細・写真・編集・CSVから対象を除き、管理者の標本一覧と確認画面には無効化済みとして残す。QRは既存の無効QRと同じ警告を返す。無効化した標本番号と詳細UUID、QR識別子を再利用しない。復旧操作は別途設計するまで設けない。
2. **完全削除**は、再認証と標本番号の再入力を伴う管理者専用操作にする。対象標本と関係行をロックし、割当QRは`retired`のまま標本参照を外して残す。標本履歴・写真のDB行を明示的に削除し、標本本体を削除する。通常の履歴削除禁止に対する、管理者の完全削除だけの例外とする。写真ファイルはDBコミット後に削除し、失敗したファイルは復旧可能な手順で後処理する。採番元は戻さず、削除した標本番号を再利用しない。詳細・写真URLは404、QR URLは無効QRの警告とする。管理操作の監査記録は秘密値を含めずに残す。
3. 無効化と完全削除のどちらも、管理者roleとMFAをサーバー側で検査し、POST時に直近のMFA再認証、CSRF、再確認を要求する。標本・QR・監査記録の変更を同じDBトランザクションにまとめ、同時編集・再実行を拒否する。GETで状態を変えない。

## 代替案と影響

| 案 | 利点 | 制約 |
|---|---|---|
| 推奨案：無効化は論理状態、完全削除は関係データを含む物理削除 | 「完全削除」の意味が明確。QR識別子と標本番号の再利用を防ぎ、既存の表示を閉じられる | 写真ファイルとDBの削除は原子的にできない。履歴・写真を消すため明示的な例外処理が必要 |
| 無効化後も通常の詳細を閲覧可能にする | 標本の研究履歴を残して利用できる | 誤登録・非公開化の目的では無効化後も情報が見える |
| 完全削除を行わず、匿名化した標本を残す | 履歴・QR参照を維持しやすい | 「完全削除」という要件と一致しない可能性が高い |

## 実装・移行の見通し

- 新しい管理状態と無効化日時・実行者、完全削除でQRの標本参照を外せる制約をマイグレーションで追加する。既存標本は有効として移行し、既存QRのtokenと割当状態を変更しない。
- 通常の検索・詳細・写真・編集・イベント・ラベル出力・CSV・QR解決・写真追加を無効化状態に沿って一括で見直す。直接URLでも認可・状態を再判定する。
- 管理画面に対象情報、関連する履歴・写真・QR件数、不可逆性を表示する。確認ページとPOSTの双方で最新状態を読む。
- テストはmember・匿名・MFA未完了の拒否、不正/古い確認、同時操作、監査失敗時のロールバック、既存URLの閉鎖、QR再利用拒否、写真削除失敗、番号不再利用を含める。PostgreSQLでも制約とトランザクションを確認する。
- 本番移行前に暗号化バックアップと復元可能性を確認する。DB移行は旧データを削除せず、完全削除の実行は管理者の個別操作に限る。

完全削除後も、既存の暗号化バックアップには保持期間中の標本データが残る。バックアップの保持規則を変える場合は別途運用判断を行う。
